# 大学祭本番に向けたリスク管理・障害対応マニュアル

StageSounds を大学祭のステージで使うときに「音が出ない」「止まらない」「操作できない」状態を
起こし得るものを、**システム的・人的・環境的**に洗い出し、それぞれの対策をまとめたものです。
「起こらないだろうが、起こそうと思えば起こせるもの」も含めています。

- **[コード]** … アプリ側で対策を実装済み（このマニュアルの作成と同時に実装）
- **[運用]** … 機材・設定・人の動きで対策するもの（チェックリストに反映）
- **[残存]** … Web アプリの仕組み上どうしても防げないもの（運用でカバー）

> 最初に知っておくべきこと
>
> 1. **本番中に止めたいときは `Esc`**。どんな画面・どんな状態でも必ず全停止します（`Space` も文字入力中以外は全停止）。
> 2. **本番 PC には GitHub Pages 版ではなくデスクトップ版（.exe / .app）を推奨**。ネット・GitHub に一切依存しません。
> 3. **予備 PC を同じ状態で用意する**のが、あらゆる障害に対する最も確実な保険です。

## 0. 前提：このアプリの構成と「大量アクセス」の影響

| 項目 | 内容 |
|---|---|
| サーバー | **なし**。GitHub Pages は HTML/JS を配るだけで、データはすべて各 PC のブラウザ内（IndexedDB）またはデスクトップ版の AppData に保存 |
| 共有データ | なし。他人が同じ URL を開いても、本番 PC の設定・音源には一切触れられない |
| ネット依存 | 初回の読み込みのみ。以後は Service Worker のキャッシュからオフライン起動できる（デスクトップ版はネット不要） |

つまり **観客や学内の人が一斉に GitHub Pages にアクセスしても、影響を受けるのは「その瞬間にページを新規に読み込もうとした PC」だけ**です。
本番 PC がすでにアプリを開いている（またはオフラインキャッシュ済み・デスクトップ版）なら、何も起きません。

ただし次のケースは起こり得ます：

- 学内 Wi-Fi は全員が同じグローバル IP から出ていくことが多く、大量アクセスや攻撃的なアクセスがあると
  **GitHub 側のレート制限が学内 IP 全体にかかり、本番 PC からも GitHub に繋がらなくなる**可能性がある
- GitHub 自体の障害（年に数回ある）
- 学内 Wi-Fi の混雑・停止、DNS 障害

→ 対策：**本番 PC はネットに繋がっていなくても動く状態で臨む**（デスクトップ版、または PWA のオフライン可を確認済み）。
ステータスバーの `オフライン可` が緑であれば、ネットが切れても再読み込み・再起動できます。

## 1. システム的リスク

### 1-1. 再生エンジン（音が止まらない／出ない）

| # | 起こり得ること | 対策 |
|---|---|---|
| S1 | フェードアウト中に PANIC STOP を押しても、フェードが終わるまで（最大5秒）音が鳴り続ける | **[コード]** フェードアウト中の音も含め、鳴っている音をすべて即停止するよう修正 |
| S2 | 画面描画のたびに AudioContext（音声スレッド）が新規作成され、長時間運用で CPU 負荷・音切れ・クラッシュに至る | **[コード]** アプリ全体で1つだけを共有するよう修正（`useRef(new AudioManager())` が毎回生成していた不具合） |
| S3 | スリープ復帰・出力デバイスの抜き差しで AudioContext が停止し、キーを押しても無音 | **[コード]** 再生時に自動復帰を試み、応答がなくても0.3秒で先へ進む。ステータスバー `AUDIO` が橙/赤ならクリックで**オーディオ再起動**（音源の再読み込み不要）。デバイス変化を検知するとトーストで警告 |
| S4 | 壊れた設定値（NaN・負数のフェード秒数）で再生時に例外が出て無音 | **[コード]** フェード秒数を常に 0〜上限に正規化。再生失敗時はトーストで通知 |
| S5 | フェードアウト中に同じキーを押し直すと、実際は鳴っているのに表示が「停止」になる | **[コード]** 修正 |
| S6 | React の例外で画面が真っ白になり、キー操作も効かず音が止められない | **[コード]** 緊急停止キーを React の外で常時監視。エラー画面にも PANIC ボタンと「その場で復旧（音は止めない）」ボタンを配置 |

### 1-2. 音源データ・保存

| # | 起こり得ること | 対策 |
|---|---|---|
| S7 | 別フォルダの**同名ファイル**（例：どちらも `track1.mp3`）を別キーに割り当てると、先に割り当てたキーまで後のファイルの音に置き換わる | **[コード]** 保存名を `track1 (2).mp3` のように自動で一意化 |
| S8 | 音源データが消えている・壊れている・未対応形式で、本番でキーを押して初めて鳴らないと気づく | **[コード]** 起動時に全音源を読み込み、失敗したタイルを**赤枠「読込失敗」**で表示。ステータスバーに `音源 12/13 失敗1` と表示。鳴らないキーを押すと理由をトースト表示 |
| S9 | 1曲の読み込み失敗で、残りの曲の読み込みも止まる／「読込中」のまま固まる | **[コード]** 曲ごとに独立して処理 |
| S10 | ブラウザが容量逼迫時やプライバシー機能（Safari の7日ルール等）で IndexedDB を削除する | **[コード]** 起動時にストレージ永続化を要求。永続化されていない場合 `保存:一時` と表示 **[運用]** 本番前に必ず `.stagepack` を書き出して USB にもバックアップ |
| S11 | シークレットモードやストレージ無効化で IndexedDB が使えず「読み込み中…」のまま固まる | **[コード]** 失敗時もメモリ上で起動し `保存不可` を赤表示 **[運用]** シークレットウィンドウで本番をしない |
| S12 | IndexedDB の接続がブラウザ側で切断され、以後の保存・読み込みがすべて失敗する | **[コード]** 切断を検知して自動再接続 |
| S13 | 容量不足で音源を保存できないのに、エラーが表示されない | **[コード]** 保存失敗・デコード失敗をトーストで通知 |
| S14 | デスクトップ版（Windows）で、日本語の長いファイル名の音源がパス長制限（260文字）を超えて保存できない | **[コード]** 保存ファイル名をハッシュ化（旧形式で保存済みのファイルも読める） |
| S15 | 不要になった音源がストレージに残り続け、容量を圧迫する | **[コード]** どのキーからも参照されなくなった音源は自動削除 |
| S16 | 長尺音源（数十分）× 多数の団体でメモリが溢れ、タブが落ちる（Chrome の「エラーコード: Out of Memory」） | **[コード]** 表示中以外の団体の音声をメモリから解放。20分超の音源は警告。ステータスバーに `MEM` 使用量を表示（1.5GB 超で橙） **[運用]** 必要な部分だけに編集した音源を使う |

### 1-3. `.stagepack` の受け渡し

| # | 起こり得ること | 対策 |
|---|---|---|
| S17 | 手で編集された・壊れた・悪意ある manifest（不正な数値、`../` を含むファイル名、巨大な文字列） | **[コード]** すべての値を検証・正規化。不正なファイル名は無視。キー配列も既定に揃える |
| S18 | 読み込み失敗時に `alert` ダイアログが出て、閉じるまで**緊急停止キーも効かない** | **[コード]** alert を廃止し、トースト表示に変更 |
| S19 | 再生中に `.stagepack` を読み込む（ドラッグしてしまう）と、団体が切り替わって音が止まる | **[コード]** 再生中は団体を追加するだけで切り替えない |
| S20 | 音源が欠けた `.stagepack` を受け取っても気づかない | **[コード]** 欠けている音源名をトースト表示＋該当タイルが赤枠 |
| S21 | 大きな団体の書き出しで、圧縮処理のため画面が数秒〜数十秒固まる | **[コード]** 音源は無圧縮で格納（mp3 等は再圧縮してもほぼ縮まない） |

### 1-4. 配信・更新（GitHub Pages / Releases / GitHub Actions）

| # | 起こり得ること | 対策 |
|---|---|---|
| S22 | 本番期間中に誰かが main に push し、壊れたビルドが公開される | **[コード]** リポジトリ変数 `DEPLOY_FREEZE=true` で Pages・Releases の自動更新を凍結できるようにした（後述） **[運用]** 本番1週間前から凍結。main ブランチ保護を設定 |
| S23 | 新バージョンが公開されると、本番中の PC が次の再読み込みで勝手に新バージョンに切り替わる | **[コード]** 自動更新を廃止。新バージョンがあってもステータスバーに `更新あり` と出るだけで、再生中は適用不可・適用時は確認ダイアログ |
| S24 | 壊れた変更がそのまま main に入る | **[コード]** PR 時に型チェック＋ビルドを行う CI を追加。デプロイ前にも成果物の健全性チェック |
| S25 | Releases の `latest` を削除→再作成する間、ダウンロードリンクが切れる。壊れたビルドを出すと前のビルドに戻せない | **[コード]** ビルドごとに `build-<番号>` の固定リリースを作成。過去のビルドがすべて残り、一つ前に戻せる |
| S26 | GitHub 障害・学内 IP のレート制限・Wi-Fi 停止で、本番 PC がアプリを開けない | **[運用]** デスクトップ版を使う／PWA の `オフライン可` を確認。デスクトップ版の exe/app を USB にも入れておく |
| S27 | GitHub アカウントの乗っ取り・リポジトリ削除・誤った force push | **[運用]** 管理者アカウントに2段階認証。デスクトップ版と `.stagepack` をローカル（USB）に保管しておけば、GitHub が消えても本番は可能 |
| S28 | GitHub Actions の依存（Rust ツールチェイン・アクション）の更新でビルドが突然壊れる | **[運用]** 本番前に動作確認済みのビルドをダウンロードしておく。凍結中は再ビルドしない |
| S29 | 偽サイト（フォーク等で作られた似た URL）を開いてしまう | **[運用]** 正しい URL をブックマーク／デスクトップ版を使う |

### 1-5. 複数起動・ブラウザ

| # | 起こり得ること | 対策 |
|---|---|---|
| S30 | 同じアプリを2つのタブ/ウィンドウで開いており、両方から音が出る・停止がもう一方に効かない・設定が上書きされる | **[コード]** 多重起動を検知して `⚠ 多重起動` を赤表示 **[運用]** 片方を閉じる |
| S31 | ブラウザの自動更新後の再起動要求、拡張機能の干渉（広告ブロッカー、翻訳ポップアップなど） | **[運用]** 本番用のブラウザプロファイル（拡張機能なし）を使う／デスクトップ版を使う |
| S32 | ブラウザの翻訳機能が画面を書き換えて表示が崩れる | **[運用]** 翻訳を「このサイトでは翻訳しない」に設定 |

## 2. 人的リスク（操作ミス・誤操作）

| # | 起こり得ること | 対策 |
|---|---|---|
| H1 | モーダル表示中・入力欄にフォーカスがある時に `Esc` / `Space` を押しても止まらない | **[コード]** `Esc` は常に全停止。`Space` は文字入力中以外は全停止 |
| H2 | 団体セレクトにフォーカスが残ったまま文字キーを押すと、**団体が切り替わって音が止まる** | **[コード]** スロットキーではセレクトが反応しないよう抑止。選択後は自動でフォーカスを外す |
| H3 | 再生中に誤って団体を切り替えて音が止まる | **[コード]** 再生中は団体セレクトを無効化 |
| H4 | ボタンにフォーカスが残り、`Enter` / `Space` / `Tab` で意図しないボタン（編集・書き出し等）が押される | **[コード]** プレイ中は `Tab` / `Enter` を無効化。`Space` は全停止に統一 |
| H5 | `F5` / `Ctrl+R` で再読み込み、`Ctrl+F`（検索バー）、`Ctrl+P`（印刷）、`Ctrl+S`、`Ctrl+L`（アドレスバー）などでフォーカスが奪われる | **[コード]** これらのショートカットを無効化 |
| H6 | `Alt+←`・マウスの「戻る」ボタンでページを離れる | **[コード]** 無効化。離脱時は確認ダイアログ |
| H7 | 右クリックメニューが開いてキー入力が効かなくなる | **[コード]** 右クリックメニューを無効化（文字入力欄を除く） |
| H8 | `Ctrl+1` などブラウザのタブ切替と同時にスロットが鳴る | **[コード]** Ctrl/Alt/Cmd 付きのキーではスロットを鳴らさない |
| H9 | 別のウィンドウ（台本、LINE、エクスプローラー等）をクリックしてしまい、以後キーが効かない | **[コード]** フォーカスが外れると画面上部に**赤い警告**を表示 **[運用]** 本番 PC で他のアプリを開かない |
| H10 | 編集完了後も団体名入力欄にフォーカスが残り、キー入力が文字入力になる | **[コード]** 編集完了時にフォーカスを外す |
| H11 | 鳴らないキーを押しても無反応で、原因が分からず焦る | **[コード]** 「読み込み中です」「音源データが見つかりません」等をトースト表示 |
| H12 | 違うキーを押す・違う団体を選んでいる | **[運用]** 団体名は画面中央に大きく表示。キー割当表（キュー表）を紙で用意し、リハーサルで通す |
| H13 | 本番中に誤って編集モードに入り、ドラッグ&ドロップで音源を差し替える／団体を削除する | **[運用]** 本番中は編集モードに入らない。削除は確認ダイアログあり。事前に `.stagepack` をバックアップ |
| H14 | `Ctrl+W` / `Alt+F4` / `Cmd+Q` でブラウザやアプリを閉じる | **[残存]** Web ページからは防げない（ブラウザ版は離脱確認ダイアログが出る）。**[運用]** 落ちたら即再起動（音源は自動復元、数秒）。予備 PC に切り替え |
| H15 | 音量の上げすぎ・PA卓側のミュート忘れ | **[運用]** 音量は PA 卓で管理。PC の音量は固定（例：100%）にし、リハで確認 |

| H17 | 共有された `.stagepack` が最新版でない | **[運用]** 書き出し時のファイル名に日付を付ける／最終版を1人が管理する |

## 4. 本番期間中のデプロイ凍結手順（S22）

1. GitHub のリポジトリ → **Settings → Secrets and variables → Actions → Variables** タブ
2. **New repository variable** で `DEPLOY_FREEZE` = `true` を作成
3. 以後、main に push されても GitHub Pages・Releases は更新されない
4. 緊急で修正版を出す必要がある場合は、Actions 画面からワークフローを手動実行し、`force_deploy` / `force_release` にチェック
5. 本番期間が終わったら変数を削除（または `false` に）

あわせて **Settings → Branches** で main にブランチ保護（PR 必須・CI 必須）を設定しておくと、誤 push 自体を防げます。

### 本番中の操作（卓に貼る用）

- **止める：`Esc`**（どんな画面でも効く）／`Space`／画面下の赤いバー
- 画面上部に**赤い警告「ウィンドウが選択されていません」** → 画面の何もないところをクリック
- キーを押しても鳴らない → 画面上部のトーストを見る／ステータスバーの `AUDIO` が緑でなければクリック（オーディオ再起動）
- 本番中は**編集モードに入らない・団体を切り替えるときは停止してから**
- `更新あり` が出ても**本番中は押さない**

## 6. 障害発生時のフロー

```text
音が止まらない
  └─ Esc → それでも止まらない → PA卓のフェーダーを下げる（最優先）→ 原因調査は後

音が出ない（キーを押しても無音）
  ├─ タイルが光る（緑）のに無音 → PA卓・ケーブル・OSの出力先を確認
  │                              → ステータス AUDIO が緑以外ならクリックしてオーディオ再起動
  ├─ タイルが赤枠「読込失敗」 → 予備PCに切り替え（本番中に音源を入れ直さない）
  ├─ 何も反応しない → 画面をクリック（フォーカス）→ もう一度押す
  └─ 画面が固まった/エラー画面 → 「その場で復旧」→ ダメなら予備PCに切り替え → 本番PCを再起動

アプリ/ブラウザが落ちた
  └─ 予備PCに切り替え（PA卓のフェーダー操作）→ 落ちたPCは再起動（音源は自動で復元される）

PCごと故障・電源断
  └─ 予備PCに切り替え。予備もない場合は USB の exe/app と .stagepack を別のPCで起動
```

**原則：本番中に「直そう」としない。止める → 予備に切り替える → 終わってから調べる。**
